Проанализировал оба demo. Вот ключевые инсайты и план:
Auction demo — уже содержит LLM-переговоры между merchant-агентами (диалоги StartDialogueBehaviour/DialogueResponderBehaviour) для формирования совместных ставок. Но нет никакой памяти о прошлых сделках: каждый аукцион начинается с чистого листа. Нет репутации, trust score, истории взаимодействий. Агенты не могут ускорить переговоры на основе опыта.
Prisoners Dilemma demo — содержит готовый механизм персонального доверия: impression_memory.py (векторное хранилище Chroma), где агенты сохраняют мнения о контрагентах после каждой игры и используют их при выборе стратегии. Есть также визуализации и сбор статистики.
Вывод для курсовой: идеальная стратегия — перенести паттерн доверия из PD в Auction. Добавить два уровня:
1. Личный (Personal Trust) — память агента о прошлых сделках с конкретным партнёром (как impression_memory).
2. Системный (System Trust) — глобальная доска рейтингов у ProposalBoardAgent.
Это позволит измерить, как доверие влияет на скорость переговоров (меньше сообщений в диалоге, быстрее согласие), частоту коллабораций и итоговую эффективность.

# План курсовой: Механизмы доверия в мультиагентных переговорах
## 1. Анализ текущих demo
### Auction (аукцион ингредиентов)
- **Архитектура**: ProposalBoardAgent (инициатор) + merchant-агенты (First/Second/Third). Используется Contract Net Protocol.
- **Переговоры**: Есть LLM-диалоги между агентами (`StartDialogueBehaviour` / `DialogueResponderBehaviour`) для формирования совместных ставок (collaboration). Диалоги ограничены 2 сообщениями, но агенты не помнят истории взаимодействий друг с другом между раундами/запусками.
- **Недостаток с точки зрения доверия**: Нет репутации, нет memory о прошлых сделках. Каждый аукцион — "tabula rasa". Агенты не могут решить "доверять ли контрагенту" и не могут ускорить переговоры на основе прошлого опыта.
- **Метрики уже есть**: цена ставки (P), себестоимость (C), резервная цена (V), маржинальность по агентам, количество раундов до стабилизации.
### Prisoners Dilemma (повторяющаяся дилемма заключенных)
- **Архитектура**: PlatformAgent управляет раундами, LLM-агенты выбирают стратегии (AC, AD, TFT, GT, FTFT).
- **Механизм доверия**: Есть `impression_memory.py` — персональное векторное хранилище (Chroma) мнений агента о других агентах. После каждой игры агент формирует impression (`FormImpressionBehaviour`), и при следующем выборе стратегии учитывает это мнение (`GetStrategyBehaviour`).
- **Эффект**: Агенты адаптируют стратегию к конкретному оппоненту на основе прошлого поведения (доверие/недоверие).
- **Визуализация**: Уже реализованы графики динамики стратегий, графы сообществ, распределение выигрышей.

## 2. Цель и гипотеза курсовой
**Цель**: Показать, как механизмы доверия (личные и системные) влияют на скорость и эффективность переговоров агентов в аукционной среде.
**Гипотезы**:
1. При наличии механизма доверия агенты быстрее достигают соглашений (меньше сообщений в диалоге, меньше раундов аукциона).
2. Агенты с высоким доверием друг к другу чаще идут на коллаборацию, что повышает вероятность покрытия заказа.
3. При отсутствии доверия (или при нарушении доверия) агенты либо отказываются от сотрудничества, либо вступают в длинные агрессивные переговоры.
4. Системный механизм доверия (глобальный рейтинг) дополняет личный, снижая риск манипуляций и "первого контакта".

## 3. Архитектура механизмов доверия для интеграции в Auction
### 3.1 Личный механизм доверия (Personal Trust)
- **Аналог**: `impression_memory` из Prisoners Dilemma.
- **Реализация**: Для каждого merchant-агента создать векторное хранилище (Chroma) или просто JSON/словарь, где он хранит факты о сделках с другими агентами.
- **Что хранить**:
  - `success: bool` — состоялась ли сделка.
  - `fair_price: bool` — были ли цены контрагента близки к ожидаемым (не было ли обмана).
  - `dialogue_length: int` — сколько шагов заняли переговоры.
  - `timestamp` — время сделки.
  - `text_impression` — текстовое резюме LLM о контрагенте (генерируется после диалога).
- **Как использовать**:
  - При выборе `CollaborationProposal.target_agent` учитывать reputation контрагента.
  - В `AUCTION_BIDDER_PROMPT` и `DIALOGUE_INITIATOR_PROMPT` добавить контекст: "Твой прошлый опыт с агентом X: ...".
  - Если trust высокий — LLM может сразу соглашаться без торга или с 1 сообщением вместо 2.
  - Если trust низкий или нет опыта — LLM торгуется агрессивнее или отказывается от коллаборации.
### 3.2 Системный механизм доверия (System/Platform Trust)
- **Идея**: ProposalBoardAgent ведёт глобальную "доску доверия" (Trust Board) — публичный рейтинг всех merchant-агентов.
- **Что хранить**:
  - `global_score: float` — накопленный рейтинг (например, +1 за успешную сделку, -2 за обман/срыв).
  - `n_deals: int`, `n_fails: int`.
  - `avg_margin: float` — средняя маржа агента (сигнал о честности ценообразования).
- **Как использовать**:
  - Merchant-агенты запрашивают у ProposalBoardAgent trust score потенциального партнёра перед началом диалога.
  - В prompts добавляется `partner_trust_score`.
  - Платформа может отклонять ставки от агентов с низким рейтингом (например, требовать более низкую цену).
### 3.3 Комбинированный механизм
- Личная память + системный рейтинг работают вместе.
- Если личный опыт положительный, но системный рейтинг низкий — агент может быть осторожен.
- Если системный рейтинг высокий, но личного опыта нет — агент быстрее идёт на сделку (эффект "репутации при первом контакте").

## 4. Пошаговый план реализации
### Шаг 2. Базовые метрики (Baseline)
- Зафиксировать метрики без доверия:
  - Среднее количество сообщений в диалоге (`dialogue_length`).
  - Среднее число раундов аукциона до завершения.
  - Процент успешных сделок (пользователь купил).
  - Процент коллаборативных ставок vs соло-ставок.
  - Итоговая цена (P) и суммарная прибыль агентов.
- Сделать 10+ прогонов для усреднения.
### Шаг 3. Реализация личного механизма доверия (Personal Trust)
- Создать `trust_memory.py` (аналог `impression_memory.py` из PD):
  - `add_trust_record(agent_id, target_id, record)` — сохранить факт сделки.
  - `get_trust_context(agent_id, target_id) -> str` — получить текстовое резюме для prompt.
- После каждого диалога (`StartDialogueBehaviour` / `DialogueResponderBehaviour`) добавить вызов LLM для формирования impression о контрагенте (как `FormImpressionBehaviour` в PD).
- Модифицировать `AuctionBidderBehaviour`:
  - Перед выбором `CollaborationProposal` извлекать `trust_context` для каждого потенциального партнёра.
  - Если trust низкий — исключить агента из списка кандидатов или снизить желаемые цены.
- Модифицировать prompts:
  - В `AUCTION_BIDDER_PROMPT` добавить поле `trust_notes`.
  - В `DIALOGUE_INITIATOR_PROMPT` и `DIALOGUE_RESPONDER_PROMPT` добавить `partner_trust_history`.
  - Если trust высокий — prompt должен мягко подталкивать к быстрому согласию.
### Шаг 4. Реализация системного механизма доверия (System Trust)
- Расширить `ProposalBoardAgent`:
  - Добавить `trust_board: Dict[str, TrustRecord]`.
  - При обновлении победной ставки пересчитывать `global_score` для участников (успех +1, если цена выше лимита и сделка сорвана по вине агента — штраф).
- Добавить поведение `TrustInfoBehaviour` — отвечает на запросы merchant-ов о рейтинге других агентов.
- Интегрировать `trust_score` в prompts merchant-ов.
### Шаг 5. Комбинированный сценарий
- Запустить аукцион с обоими механизмами одновременно.
- Проверить гипотезу о синергии (личный опыт + системный рейтинг).
### Шаг 6. Эксперименты и сравнение
- Провести серии запусков для 4 конфигураций:
  1. **Baseline** — без доверия (текущий код).
  2. **Personal Trust only** — только личная память.
  3. **System Trust only** — только глобальный рейтинг.
  4. **Combined** — оба механизма.
- Для каждой конфигурации собрать:
  - `avg_dialogue_messages` (средняя длина переговоров).
  - `avg_auction_rounds` (скорость сходимости аукциона).
  - `deal_success_rate` (процент успешных покупок).

## 5. Ключевые инсайты из существующего кода
1. **Переговоры уже есть**: В `auction` уже реализованы LLM-диалоги. Не нужно писать переговоры с нуля — нужно только "научить" агентов помнить опыт.
2. **Memory уже есть**: В `prisoners_dillema` есть готовый паттерн `impression_memory` с Chroma. Его можно адаптировать с минимальными изменениями.
3. **Метрики уже есть**: `auction` сохраняет `winning_bid_split` с метриками 1 и 2. Это база для сравнения эффективности.
4. **Prompt engineering**: Поведение агентов полностью управляется через prompts (`agent_prompts.py`). Добавление trust — это в основном добавление переменных в prompt и логики перед вызовом LLM.
5. **Визуализацию можно позаимствовать**: `visualisation.py` из PD содержит шаблоны для matplotlib/seaborn — адаптировать под auction-метрики несложно.

## 6. Риски и mitigation
| Риск | Mitigation |
|------|------------|
| LLM нестабильно следует trust-инструкциям в prompt | Добавить few-shot примеры в prompt; использовать structured output (Pydantic) для решений |
| Нет репрезентативной выборки (случайность в LLM) | Делать 10–20 прогонов на сценарий, усреднять метрики |
| Сложность отделения эффекта доверия от других факторов | Контролировать random seed, фиксировать shop_sku, использовать одинаковые начальные условия |
| Длинные диалоги замедляют симуляцию | Уменьшить `time_to_wait_for_proposals` и `timeout` в тестовом режиме; использовать in-memory messaging |
